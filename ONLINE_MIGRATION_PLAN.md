# План переноса Devis Studio: offline → online

Документ описывает, что потребуется, чтобы текущее локальное приложение (IndexedDB в браузере) стало доступным онлайн: с сохранением данных на сервере, входом и (при необходимости) доступом с нескольких устройств.

Это **план**, не реализация. Текущий MVP по `SPEC.md` остаётся локальным, пока не будет отдельного решения начать онлайн-этап.

---

## 1. Зачем переходить в online

| Цель | Что даёт online |
|------|-----------------|
| Данные не привязаны к одному браузеру | Серверная БД + бэкапы на стороне хостинга |
| Работа с телефона и ПК | Один аккаунт, общая база |
| Меньше риска «очистил данные сайта» | Persistence вне профиля браузера |
| (Опционально) доступ помощнику / бухгалтеру | Роли и приглашения позже |

**Не обязательно сразу:** командная работа, публичный сайт для клиентов, интеграции с маркетплейсами.

---

## 2. Что уже есть и что переиспользуем

Сохраняем без переписывания с нуля:

- UI на Next.js (App Router) + SCSS Modules
- Модель данных: `Client`, `Order`, `OrderItem`, `Payment` (копейки, UUID, статусы)
- Бизнес-логику расчётов (`lib/services/money`, статусы оплаты, Zod)
- Экспорт/импорт JSON как инструмент **миграции** старых локальных данных на сервер

Меняем:

- Хранилище: IndexedDB/Dexie → серверная БД
- Слой `repositories/*`: вместо Dexie — HTTP API (или Server Actions к БД)
- Появляется авторизация и изоляция данных по пользователю

---

## 3. Целевая архитектура (рекомендуемая)

Простой вариант «одного стека» под уже выбранный Next.js:

```text
Браузер (Next.js UI)
        │
        ▼
Next.js на хостинге  ──►  API / Server Actions
                                │
                                ▼
                         PostgreSQL (основная БД)
                                │
                         (опц.) объектное хранилище
                         для будущих вложений
```

### Почему так

- Не нужен отдельный бэкенд на другом языке на старте
- Одна кодовая база, один деплой
- PostgreSQL надёжнее SQLite на «настоящем» облачном хостинге при нескольких устройствах
- Zod-схемы можно переиспользовать на сервере для валидации API

### Альтернативы (если понадобится)

| Вариант | Когда имеет смысл |
|---------|-------------------|
| Next.js + SQLite (Turso / LibSQL) | Очень маленький трафик, один пользователь, проще старт |
| Отдельный API (Nest/Fastify) + Next | Если позже появятся мобильное приложение и много интеграций |
| Supabase / Firebase | Быстрый BaaS: auth + БД из коробки; меньше контроля, vendor lock-in |
| Electron/Tauri + локальный SQLite | Не «online», а «десктоп с файлом на диске» |

**Рекомендация для Devis Studio:** Next.js + PostgreSQL + сессии/JWT (или Auth.js).

## 4. Что потребуется по компонентам

### 4.1. Приложение (код)

1. **Схема БД** (миграция Prisma / Drizzle) — таблицы как сейчас + `userId` / `workspaceId`
2. **Auth** — регистрация/вход (email+пароль или magic link), выход, смена пароля
3. **API или Server Actions** — CRUD клиентов, заказов, платежей; те же правила денег и запрет переплаты
4. **Замена репозиториев** — UI почти тот же, источник данных — сервер
5. **Импорт локального бэкапа** — «Загрузить JSON из старой версии» в аккаунт один раз
6. **HTTPS**, переменные окружения, секреты не в git

### 4.2. База данных

- **PostgreSQL 15+**
- Ежедневные автоматические бэкапы (у хостера или `pg_dump` по cron)
- Точка восстановления перед крупными миграциями

### 4.3. Авторизация и безопасность

- Хеширование паролей (argon2 / bcrypt)
- CSRF-защита для cookie-сессий
- Rate limit на login
- Доступ только к своим записям (`WHERE user_id = …`)
- Позже: 2FA (по желанию)

### 4.4. Домен и сертификат

- Домен (например `crm.devis.studio` или любой `.ru` / `.com`)
- HTTPS (Let’s Encrypt — обычно бесплатно у хостера / через Cloudflare)

### 4.5. Почта (желательно сразу)

- Для сброса пароля и подтверждения email
- Сервисы: Resend, Postmark, или SMTP хостера / Yandex 360 для домена

## 5. Хостинг и серверы: варианты

Ниже — практичные связки. Цены ориентировочные на 2026, уточнять на сайтах провайдеров.

### Вариант A — «быстрый старт» (рекомендуется для одного пользователя)

| Слой | Сервис | Зачем |
|------|--------|--------|
| Frontend + API | **Vercel** или **Railway** / **Render** | Деплой Next.js |
| PostgreSQL | **Neon**, **Supabase DB**, **Railway Postgres**, **ElephantSQL** | Управляемая БД |
| DNS / HTTPS | Cloudflare + свой домен | SSL, кэш статики |
| Почта | Resend | Письма auth |

**Плюсы:** мало админки, автодеплой из GitHub.
**Минусы:** часть сервисов — зарубежные; для РФ смотреть доступность оплаты и latency.

Ориентир: **$0–25/мес** на старте (часто есть free tiers с лимитами).

### Вариант B — «всё в РФ / СНГ»

| Слой | Сервис | Зачем |
|------|--------|--------|
| VPS или PaaS | **Timeweb Cloud**, **Selectel**, **Yandex Cloud**, **Reg.ru VPS** | VM или контейнер с Node |
| PostgreSQL | У того же провайдера (managed) или на VPS в Docker | БД рядом |
| Reverse proxy | Nginx / Caddy | HTTPS |
| Деплой | Docker Compose + GitHub Actions | Сборка и выкат |

**Плюсы:** данные и биллинг в привычной юрисдикции.
**Минусы:** больше самостоятельной настройки (обновления, firewall, бэкапы).

Ориентир VPS: **400–1500 ₽/мес** за маленький инстанс + диск под бэкапы.

### Вариант C — «минимум возни с БД» (BaaS)

| Слой | Сервис |
|------|--------|
| Auth + Postgres + Storage | **Supabase** или **Appwrite** (self-host / cloud) |
| UI | Next.js на Vercel / VPS |

**Плюсы:** быстрый auth и RLS.
**Минусы:** сильнее привязка к платформе; бизнес-правила всё равно писать на сервере.

### Вариант D — только статика (не подходит как «настоящий online»)

Выложить `next export` / статический билд на GitHub Pages **без** серверной БД — данные снова останутся в IndexedDB браузера. Это **не** решает задачу сохранности на сервере.

## 6. Рекомендуемый стек для реализации

| Область | Выбор |
|---------|--------|
| UI | Текущий Next.js 16 + React |
| ORM | **Drizzle** или **Prisma** |
| БД | **PostgreSQL** |

## 7. Перенос существующих локальных данных

Сейчас у вас уже есть формат бэкапа:

`devis-studio-backup-YYYY-MM-DD.json`

### Процедура миграции пользователя

1. В **локальной** версии: Настройки → Экспорт JSON
2. Завести аккаунт в online-версии
3. В online: «Импорт из локальной версии» (тот же JSON)
4. Сервер валидирует файл (как сейчас) и записывает строки с привязкой к `userId`
5. Проверить обзор, клиентов, заказы, оплаты
6. Локальную копию оставить как архив; дальше работать только в online (или сделать режим «только чтение» локально)

### Технические правила импорта на сервер

- Те же проверки связей и арифметики, что в MVP
- Пересчёт `totalMinor` / `paidMinor` на сервере
- Не выполнять код из JSON
- По желанию: запретить повторный импорт без подтверждения «заменить все мои данные»

## 8. Поэтапный план работ

### Этап O0. Решение и инфраструктура (1–3 дня)

- Выбрать вариант хостинга (A / B / C)
- Купить/привязать домен
- Создать пустой PostgreSQL
- Репозиторий + CI (lint/test/build)
- Секреты: `DATABASE_URL`, `AUTH_SECRET`, SMTP

### Этап O1. Auth и изоляция данных (3–7 дней)

- Регистрация / вход / выход
- Таблица пользователей
- Middleware: защищённые маршруты
- Страницы login/register на русском

### Этап O2. Серверная модель и API (1–2 недели)

- Миграции таблиц 1:1 с текущей моделью + `userId`
- CRUD клиентов / заказов / платежей на сервере
- Переключить UI с Dexie на API (постепенно: сначала клиенты, потом заказы)
- Сохранить unit-тесты денег; добавить тесты API

### Этап O3. Импорт локального бэкапа (2–4 дня)

- Endpoint импорта JSON в аккаунт
- UI в настройках
- Чеклист проверки после импорта

### Этап O4. Деплой, HTTPS, бэкапы (2–4 дня)

- Production-деплой
- Автобэкапы Postgres
- README online: URL, вход, импорт, восстановление

### Этап O5. Улучшения (по необходимости)

- Работа с двух устройств одновременно (оптимистичные обновления / конфликт «последняя запись»)
- Экспорт JSON уже с сервера (как сейчас)
- 2FA, приглашение второго пользователя
- PWA только если явно нужен офлайн-кэш **поверх** серверной БД

---

## 9. Что станет с «офлайн»

| Режим | Описание |
|-------|----------|
| Online-first (цель) | Без сети нельзя менять данные; при появлении сети — обычная работа |
| Offline-tolerant (позже) | Очередь изменений на устройстве + синхронизация (сложнее, отдельный проект) |

Для личного CRM обычно достаточно **online-first** + регулярный серверный бэкап Postgres.
PWA не заменяет серверную БД и не даёт «100% сохранности» сама по себе.

## 10. Оценка трудозатрат и бюджета

| Статья | Оценка |
|--------|--------|
| Разработка O0–O4 | примерно 3–6 недель спокойной работы (один разработчик, familiar с кодовой базой) |
| Хостинг старт | ~0–25 USD/мес или ~500–2000 ₽/мес |
| Домен | ~100–1000 ₽/год |
| Почта | часто бесплатный стартовый тариф |

Точные сроки зависят от выбора Auth/хостинга и того, нужен ли сразу multi-user.

---

## 11. Риски и как снизить

| Риск | Мера |
|------|------|
| Потеря данных при миграции | Двойной JSON-бэкап до импорта; тест на копии |
| Утечка чужих данных | Жёсткий `userId` в каждом запросе + тесты авторизации |
| Даунтайм VPS | Managed Postgres + мониторинг uptime |
| Vendor lock-in | Стандартный PostgreSQL + свой код Next.js |
| Доступность зарубежных хостингов | Иметь план B на РФ VPS |

## 12. Чеклист «можно запускать online»

- [ ] Домен открывается по HTTPS
- [ ] Регистрация и вход работают
- [ ] Данные разных пользователей не пересекаются
- [ ] Клиенты / заказы / оплаты создаются на сервере
- [ ] Импорт локального JSON проверен на реальном бэкапе
- [ ] Бэкапы Postgres настроены и проверен restore
- [ ] Секреты не в репозитории
- [ ] README обновлён под online

## 13. Рекомендуемое решение «по умолчанию»

Для личного Devis Studio с учётом решений из §14:

1. **Код:** Next.js (как сейчас) + PostgreSQL + Auth.js (email/password, один пользователь)
2. **Хостинг:** **РФ** — Timeweb / Selectel / Yandex Cloud (приложение + managed Postgres или Postgres в Docker)
3. **Миграция данных:** экспорт JSON из локальной версии → импорт в аккаунт → дальше только online
4. **Сохранность:** автобэкапы Postgres + ручной экспорт JSON из настроек

Можно начинать этап **O0** (выбор конкретного РФ-провайдера, VPS/БД, домен) без ломки текущего локального MVP до готовности импорта.

## 14. Решения перед стартом O0

Зафиксировано:

| # | Вопрос | Решение |
|---|--------|---------|
| 1 | Пользователи | **Только один пользователь** (без командного доступа и ролей на старте) |
| 2 | Хостинг / юрисдикция | **РФ** (VPS или PaaS: Timeweb / Selectel / Yandex Cloud и т.п.) |
| 3 | Вход | **Email + пароль** (без OAuth Google/Yandex на старте) |
| 4 | Локальная версия | **Полный переход на online**; локальный IndexedDB-режим после миграции не поддерживаем как основной |

### Следствия для реализации

- Auth упрощённый: один аккаунт владельца (регистрация можно ограничить invite-кодом или одноразовой установкой, чтобы чужие не регистрировались на вашем инстансе).
- Хостинг по **варианту B** из раздела 5 (РФ), не Vercel/Neon как основной путь.
- После успешного импорта JSON и проверки данных — работать только с серверной БД; локальный MVP считать архивом для переноса.
- Multi-user, OAuth и гибрид offline+online — вне текущего scope.
