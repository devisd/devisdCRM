# ТЗ: локальная система учёта клиентов и заказов — Devis Studio

## 1. Задача

Создать личное приложение для учёта клиентов, заказов, выполненных работ, стоимости и оплат. Пример: клиент заказал 15 карточек для Wildberries; нужно записать клиента, перечень работ, количество, цену, сроки, статус и оплаты, а позже открыть клиента и увидеть всю историю сотрудничества.

Это локальное приложение для одного пользователя. На первом этапе без сервера, аккаунтов, облака и интеграций.

## 2. Стек и ограничения

- Next.js (App Router), React, TypeScript strict.
- SCSS Modules.
- IndexedDB через Dexie.js — основное хранилище. Не использовать localStorage как базу данных.
- Zod для проверки данных; React Hook Form — только если действительно нужен.
- date-fns и Lucide React допустимы при необходимости.
- Весь интерфейс на русском.
- Адаптивность: desktop, tablet, mobile.
- Сначала изучить существующий репозиторий и версии зависимостей; не переписывать рабочий код без причины.
- Не добавлять Redux или сложное глобальное состояние без необходимости.
- Не создавать PWA, Service Worker, backend или API в MVP. Важно: проверить, что означает «офлайн» для выбранной среды. После первой загрузки CRUD должен работать без сети; повторное открытие без сети требует доступности файлов приложения. Если без кэширования ресурсов это невозможно, описать ограничение и предложить минимальный вариант отдельно, не подключая PWA самовольно.
- Не отправлять пользовательские данные в сеть и не подключать аналитику.
- Денежные значения хранить целыми числами в копейках, а отображать в рублях. Не использовать floating point для расчётов.

## 3. MVP

Входит:
1. Обзор с показателями.
2. Список, создание, редактирование, просмотр и архивирование клиентов.
3. Список, создание, редактирование, просмотр и архивирование заказов.
4. Несколько позиций работ в одном заказе.
5. Автоматический расчёт стоимости и скидки.
6. Статусы заказа и сроки.
7. Частичные оплаты, история платежей и остаток.
8. История всех заказов в карточке клиента.
9. Поиск, фильтры и сортировка.
10. Экспорт/импорт резервной копии JSON.
11. Адаптивный интерфейс, обработка ошибок и README.

Не входит: сервер, облачная синхронизация, авторизация, командная работа, интеграции с Telegram/MAX/маркетплейсами, счета, налоги, вложения, загрузка изображений и push-уведомления. Не добавлять неработающие кнопки-заглушки.

## 4. Навигация и страницы

- `/` — обзор.
- `/orders` — список заказов.
- `/orders/new` — новый заказ.
- `/orders/[id]` — карточка заказа.
- `/orders/[id]/edit` — редактирование заказа.
- `/clients` — список клиентов.
- `/clients/new` — новый клиент.
- `/clients/[id]` — карточка клиента.
- `/clients/[id]/edit` — редактирование клиента.
- `/settings` — настройки, экспорт и импорт.

Использовать App Router. Все обращения к IndexedDB выполнять только на клиенте; не обращаться к `window`/`indexedDB` во время SSR. Обрабатывать загрузку, ошибку базы и отсутствующую запись.

## 5. Модель данных

Все сущности имеют UUID. Технические метки времени хранить в ISO-формате. Даты заказов и платежей показывать в локальном часовом поясе.

### Client
- `id: string`
- `name: string` — обязательное имя/название
- `contactName?: string`
- `phone?: string`
- `email?: string`
- `telegram?: string`
- `maxContact?: string`
- `otherContact?: string`
- `source?: string` — источник клиента
- `notes?: string`
- `tags?: string[]`
- `isArchived: boolean`
- `createdAt: string`
- `updatedAt: string`

Контакты необязательны: клиент может общаться через любой удобный канал.

### Order
- `id: string`
- `number: number` — последовательный локальный номер
- `clientId: string`
- `title: string` — например «Карточки товара для Wildberries»
- `description?: string`
- `status: "new" | "in_progress" | "waiting" | "completed" | "cancelled"`
- `orderDate: string`
- `dueDate?: string`
- `completedAt?: string`
- `discountMinor: number` — скидка в копейках, по умолчанию 0
- `totalMinor: number` — рассчитываемое итоговое значение
- `paidMinor: number` — рассчитываемое значение из платежей
- `notes?: string`
- `isArchived: boolean`
- `createdAt: string`
- `updatedAt: string`

Статусы: Новый, В работе, Ожидает ответа/материалов, Завершён, Отменён. Статус оплаты не редактировать вручную — вычислять по платежам.

### OrderItem
- `id: string`
- `orderId: string`
- `name: string`
- `description?: string`
- `quantity: number`
- `unit: string` — «шт.», «час», «комплект», «проект» или другое
- `unitPriceMinor: number`
- `lineTotalMinor: number` — количество × цена
- `sortOrder: number`

В заказе должна быть минимум одна позиция. Количество и цена не могут быть отрицательными; количество строго больше нуля. Для штучных работ (например, карточек) количество должно быть целым.

### Payment
- `id: string`
- `orderId: string`
- `amountMinor: number` — сумма в копейках, строго больше нуля
- `paymentDate: string`
- `method: "cash" | "bank_transfer" | "other"`
- `comment?: string`
- `createdAt: string`

Методы оплаты: Наличные, Перевод, Другое. В первой версии возвраты и переплаты не поддерживаются.

## 6. Бизнес-правила

1. Сумма позиции = количество × цена за единицу.
2. Итог заказа = сумма позиций − скидка.
3. Скидка не может быть отрицательной или превышать сумму позиций.
4. Сумма оплат = сумма всех платежей, привязанных к заказу.
5. Остаток = `max(итог − сумма оплат, 0)`.
6. Статус оплаты вычислять: `unpaid`, `partially_paid`, `paid`. Если итог равен нулю, показывать «Не требуется», а не «Не оплачен».
7. Нельзя сохранить платёж, превышающий остаток.
8. Отменённые заказы сохранять в истории, но не включать в доход и активные заказы.
9. Доход за период считать по реально полученным платежам за этот период, а не по сумме созданных заказов.
10. При редактировании цены уже оплаченного заказа не допускать противоречия, при котором сумма оплат выше нового итога: показать предупреждение и предложить сначала скорректировать данные.
11. Рассчитываемые суммы всегда пересчитывать из исходных позиций и платежей; не доверять рассчитанным полям импортируемого файла.
12. Физическое удаление клиента с заказами запрещено. Использовать архивирование, чтобы не терять историю.

## 7. Пользовательские сценарии

### Новый клиент
Пользователь открывает «Клиенты» → «Добавить клиента» → вводит имя и необязательные контакты/заметки → сохраняет. Запись остаётся после перезагрузки страницы.

### Новый заказ
Пользователь выбирает клиента, название, дату и при необходимости срок. Добавляет позиции: например «Дизайн карточки товара», количество 15, единица «шт.», цена за единицу. Итог пересчитывается автоматически. Можно добавить другие виды работ, скидку и заметки. После сохранения заказ виден в списке и в карточке клиента.

Пример цены в документации — только иллюстрация. Не задавать цены как реальный прайс пользователя и не предзаполнять новые заказы произвольными ценами.

### Оплата
На странице заказа нажать «Добавить оплату», указать сумму, дату, метод и комментарий. После сохранения обновить общую сумму оплат, остаток, статус оплаты и список платежей.

### История клиента
В карточке клиента показать контакты, заметки, число заказов, сумму заказов (отменённые исключить и пояснить это), фактически полученные оплаты, остаток по неоплаченным заказам и хронологический список заказов. У каждого заказа показывать дату, название, статус, итог, оплачено и остаток. Добавить действие «Создать заказ для этого клиента».

## 8. Требования к экранам

### Обзор
Компактные карточки: заказов в работе, новых заказов, получено оплат за текущий месяц, ожидается оплаты, завершено за текущий месяц. Ниже — последние заказы и ближайшие сроки. Быстрые действия: «Новый заказ», «Добавить клиента». Для пустой базы показывать понятное начало работы, а не фальшивую статистику.

### Заказы
На широком экране показывать номер, название, клиента, дату, срок, статус, итог, оплачено, остаток. На телефоне использовать карточки. Поддержать поиск по номеру/названию/клиенту, фильтры по статусу заказа и оплаты, период, сортировку по дате/номеру/сумме/сроку, архивный фильтр и сброс фильтров. Отличать «нет записей» от «ничего не найдено».

### Карточка заказа
Показывать клиента со ссылкой, номер, статус, даты, позиции, количество, цену, суммы, скидку, итог, платежи, оплачено, остаток, описание и заметки. Действия: редактировать, добавить оплату, изменить статус, архивировать. Физическое удаление не делать основным действием.

### Форма заказа
Логические блоки: клиент и основные данные; позиции; скидка и итог; сроки и статус; описание и заметки. Можно добавлять/удалять/переупорядочивать позиции. При уходе с несохранённой формы предупреждать пользователя. Проверять обязательные поля, валидные даты, цену и количество, скидку, а также исключать `NaN`/`Infinity`.

### Клиенты
Показывать имя, контакты, количество заказов, дату последнего заказа и сумму полученных оплат. Поддержать поиск по имени/названию/телефону/email/контактам, фильтр архивных, сортировку и переход в карточку.

### Настройки
Экспорт JSON, импорт JSON, создание тестовых данных только по явному действию, безопасная очистка базы с подтверждением. Объяснить, что данные хранятся локально в браузере и не отправляются на сервер, а очистка данных браузера или потеря устройства может привести к потере информации. Рекомендовать регулярно делать резервные копии.

## 9. UI/UX

Спокойный современный интерфейс с приоритетом читаемости и скорости. Светлая тема по умолчанию. Не перегружать градиентами, тенями, графиками и анимациями. Единые отступы, типографика, радиусы, цвета статусов. Цвет не должен быть единственным способом передачи статуса. У всех полей — подписи, у кнопок — понятные названия. Нужны состояния загрузки, пустого списка, ошибки, hover/focus/disabled. На мобильных экранах не должно быть горизонтального переполнения.

## 10. Локальная база

Использовать Dexie.js и IndexedDB. Предлагаемые таблицы: `clients`, `orders`, `orderItems`, `payments`, при необходимости `appMeta`. Индексы добавить по реально используемым запросам: ID, связи `clientId`/`orderId`, номер заказа, дата, статус, архивность.

Правила:
- доступ к БД вынести из компонентов в репозитории/сервисные функции;
- создание заказа и позиций выполнять транзакционно;
- операции с платежами и заказами согласовывать;
- не оставлять заказ без существующего клиента;
- клиента с историей архивировать, а не удалять;
- ошибки БД показывать понятным сообщением;
- CRUD должен переживать перезагрузку;
- обработать отсутствие/недоступность IndexedDB;
- не подменять пользовательские данные серверными mock-данными.

Пример структуры (адаптировать к существующему проекту):

```text
src/
  app/
  components/
    layout/
    ui/
    forms/
    orders/
    clients/
  lib/
    db/
    repositories/
    services/
    validation/
    format/
  types/
```

Не создавать файлы ради формальной структуры: группировать код по реальной ответственности.

## 11. Резервная копия JSON

Пример:

```json
{
  "app": "Devis Studio Work Tracker",
  "backupVersion": 1,
  "exportedAt": "2026-10-23T07:00:00.000Z",
  "data": {
    "clients": [],
    "orders": [],
    "orderItems": [],
    "payments": []
  }
}
```

Экспортировать все сущности и версию формата. Имя файла: `devis-studio-backup-YYYY-MM-DD.json`.

Импорт должен:
- проверить формат, версию, обязательные поля, уникальность ID, допустимые статусы и арифметику;
- проверить связи: каждый заказ ссылается на клиента, каждая позиция и платёж — на существующий заказ;
- отклонять некорректный файл без изменения текущей базы;
- перед импортом предупреждать, что текущие данные будут заменены;
- в MVP поддерживать полную замену базы, не автоматическое слияние;
- по возможности выполнять замену транзакционно;
- после успешного импорта обновлять UI и показывать число импортированных записей;
- не выполнять код из JSON и не использовать `eval`.

## 12. Архитектура и качество

Предпочитать простые сервисы для расчётов, форматирования валюты, дат, экспорта/импорта и сводной статистики. Использовать Zod для форм и импортируемых данных. Типы не дублировать. Не использовать `dangerouslySetInnerHTML` для заметок. Не выводить технические стектрейсы пользователю.

Покрыть unit-тестами:
- сумму позиции и заказа;
- скидку и ограничения;
- статусы оплаты и остаток;
- запрет переплаты;
- нулевой итог;
- исключение отменённых заказов из дохода;
- проверку резервной копии и связей сущностей.

Проверить сценарии: создание клиента и чтение после перезагрузки; заказ с несколькими позициями; редактирование суммы; несколько частичных платежей; история клиента; экспорт и восстановление; отклонение некорректного файла без изменения БД; архивирование клиента с заказами; работа в офлайн-сценарии.

### Этап 2. Типы, БД и расчёты

## 15. Инструкции Cursor

1. Прочитай документ целиком и начни только с Этапа 0.
2. Не создавай всё приложение одним большим изменением.
3. Перед каждым этапом кратко опиши план и затрагиваемые файлы.
4. После каждого этапа запускай релевантные проверки и исправляй ошибки, вызванные изменениями.
5. Не удаляй существующий код без обоснования.
6. Не добавляй зависимости без необходимости.
7. Не придумывай данные пользователя, цены или выполненные функции.
8. Если требование существенно неоднозначно, задай конкретный вопрос; если нет — выбери простое решение и задокументируй его.
9. В отчёте указывай изменённые файлы, команды и реальные результаты. Не заявляй о проверке, которую не запускал.
10. В конце обнови README.
11. После аудита покажи план и дождись подтверждения перед Этапом 1. Если пользователь явно попросит работать без пауз, двигайся последовательно по этапам.
