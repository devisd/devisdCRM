## 1. Резюме

- В текущей CRM **нет ни одного ограничения длины строк**: ни `.max()` в Zod (`schemas.ts`, `clientForm.ts`, `orderForm.ts`, `paymentForm.ts`), ни `maxLength` в полях ввода. Валидация бэкапа (`backupFileSchema`) тоже принимает строки любой длины.
- Все лимиты длины в `001_init.sql` существуют **только в SQL**: 10 пользовательских полей `VARCHAR(255)` и `unit VARCHAR(64)`. Кроме того, `TEXT`-поля (`notes`, `description`, `comment`) ограничены 65 535 байтами — этого лимита тоже нет в Zod.
- Отсюда риск: корректный по текущим правилам JSON-бэкап может не восстановиться в MySQL (ошибка в строгом режиме) или восстановиться с **молча обрезанными** строками (без `STRICT_TRANS_TABLES`).
- Индексация по строкам реально нужна только для `clients.name` (сортировка списка клиентов). Уникальных строковых ограничений нет. Поиск в CRM — подстрока в памяти (`includes`), на сервере это `LIKE '%…%'`, который обычный индекс не использует.
- `orders.number INT UNSIGNED` (до 4 294 967 295) уже диапазона, который допускает Zod (`z.number().int().positive()` принимает до 2⁵³−1 — проверено на Zod 4.6.7). Тот же разрыв у `order_items.sort_order`.
- **Рекомендация — гибрид:** зафиксировать лимиты в Zod для коротких полей (оставить `VARCHAR`), перевести в `TEXT` только свободное поле `other_contact`, задать в Zod верхнюю границу для `TEXT`-полей и для номера заказа. Применять — только после проверки реальных данных (раздел 7) и отдельного согласования.

## 4. Особенности, влияющие на выбор

1. **Единицы длины различаются.** MySQL считает `VARCHAR(n)` в символах (кодовых точках), JS `.length` — в UTF-16-единицах. Эмодзи: `'😀'.length === 2`, а MySQL считает 1. Поэтому `z.string().max(n)` **никогда не пропустит** строку длиннее `VARCHAR(n)`: Zod строже или равен. В будущем PHP API нужно считать длину через `mb_strlen()` (кодовые точки), как MySQL.
2. **Граница `TEXT` — в байтах.** Один UTF-16-юнит JS даёт в UTF-8 не более 3 байт (суррогатная пара — 4 байта на 2 юнита). Значит, `.max(21845)` гарантирует ≤ 65 535 байт; удобная граница с запасом — `.max(20000)`.
3. **Индексы.** Полный индекс по `TEXT` невозможен, только префиксный. Поэтому `clients.name` (единственная индексируемая строка) должен остаться `VARCHAR`. Предел полного индекса InnoDB — 3072 байта, то есть `VARCHAR(768)` в utf8mb4; 255 — с большим запасом.
4. **Размер строки InnoDB.** Сумма `VARCHAR` в таблице ≤ 65 535 байт. Сейчас в `clients` 8 × 255 × 4 = 8160 байт — запас большой, увеличение лимитов не упрётся в предел.
5. **`TEXT` в MySQL 8** не мешает сравнению и `LIKE`. Нюанс: сортировка по `TEXT` учитывает только первые `max_sort_length` байт (по умолчанию 1024), а внутренние временные таблицы могут уходить на диск — для неиндексируемых полей CRM это несущественно.
6. **Строгий режим.** Без `STRICT_TRANS_TABLES` превышение лимита не даёт ошибку, а обрезает данные. Это делает проверку в Zod/API обязательной при любом варианте (аудит 3.2.1, S1).

## 5. Варианты решения

### Вариант A. Лимиты в Zod + понятные ошибки API, схема без изменений

Добавить `.max()` во все сущностные и формовые схемы по значениям SQL; API возвращает 422 с путём поля.

| Плюсы | Минусы |
|-------|--------|
| Один источник правды: Zod = SQL | Новое правило для пользователя: существующие длинные значения станут невалидными |
| Ошибка видна в форме до сохранения, а не на сервере | **Импорт бэкапа отклоняется целиком**, если хоть одно поле длиннее лимита. Это блокирует перенос данных |
| Схема и индексы остаются компактными | `other_contact` в 255 символов неудобен для свободных заметок о контактах |
| Защищает от обрезания при нестрогом `sql_mode` | Затрагивает frontend-валидацию — нужно согласование и тесты |

### Вариант B. `TEXT` для всех неиндексируемых строк

`VARCHAR` остаётся только у `clients.name`; остальные пользовательские строки — `TEXT`.

| Плюсы | Минусы |
|-------|--------|
| Не вводит новых лимитов в интерфейсе | Граница не исчезает, а сдвигается к 65 535 байт — её всё равно нужно отразить в Zod |
| Бэкап с длинными контактами восстановится | Нельзя проиндексировать эти поля полностью в будущем (только префиксный индекс) |
| | Слабая модель данных: телефон, email, единица на 64 КБ — нет сигнала об ошибке ввода |
| | Тот самый «автоматический перевод всего в TEXT», против которого предупреждает задача |

### Вариант C (рекомендуемый). Гибрид по смыслу поля

| Группа | Поля | Решение |
|--------|------|---------|
| Индексируемое имя | `clients.name` | `VARCHAR(255)` + Zod `.max(255)` |
| Короткие идентифицирующие строки | `orders.title`, `order_items.name` | `VARCHAR(255)` + Zod `.max(255)` |
| Короткие контакты | `contact_name`, `phone`, `email`, `telegram`, `max_contact`, `source` | `VARCHAR(255)` + Zod `.max(255)` |
| Единица измерения | `order_items.unit` | `VARCHAR(64)` + Zod `.max(64)` |
| Свободный контакт | `clients.other_contact` | **`TEXT`** + Zod `.max(20000)` |
| Длинные тексты | `notes`, `description`, `comment` (5 полей) | `TEXT` без изменений + Zod `.max(20000)` |
| Номер заказа | `orders.number` | `INT UNSIGNED` без изменений + Zod `.max(4_294_967_295)` |
| Порядок позиции | `order_items.sort_order` | `INT UNSIGNED` без изменений + Zod `.max(4_294_967_295)` |
| Служебные | `app_meta.*`, `schema_migrations.version`, `tags` | без изменений |

| Плюсы | Минусы |
|-------|--------|
| Лимиты осмысленные и совпадают в Zod, API и SQL | Меняются и SQL (одно поле), и Zod (≈ 18 полей) — нужно согласование |
| Индекс `clients.name` сохраняется | Импорт старых бэкапов с длинными значениями всё ещё отклоняется — нужна проверка данных (раздел 7) |
| Свободное поле контактов не ограничено искусственно | Добавляются проверки в формах (UX: показывать ошибку или ставить `maxLength`) |
| Не зависит от `sql_mode`: обрезание исключено валидацией | |

Вариант C сводит требование задачи — «понятные ошибки вместо отказа или обрезания в БД» — к минимальному изменению схемы.

### Альтернатива для `orders.number`: `BIGINT UNSIGNED`

Расширение типа до `BIGINT` устраняет расхождение со стороны БД, но не убирает потребность в верхней границе: значения выше 2⁵³−1 небезопасны в JS и при JSON-сериализации. Граница в Zod нужна в обоих случаях, поэтому проще оставить `INT UNSIGNED` (4 байта вместо 8 и в индексе уникальности) и ограничить Zod. Последовательная выдача номеров с 1 не приблизится к 4,29 млрд.

## 7. Вопросы, требующие проверки реальных данных

1. **Есть ли реальные данные или резервные копии** у пользователя: в браузерах, где использовалась локальная версия, или в файлах `devis-studio-backup-*.json`? В плане миграции было сказано, что реальных данных для переноса нет, — это нужно подтвердить до введения лимитов.
2. Если копии есть — **максимальная длина каждого поля** в них. Достаточно одноразового локального подсчёта по JSON (без отправки файла куда-либо). Особенно важны `otherContact`, `title`, позиции `name`, `unit` и `notes`.
3. **`sql_mode` и версия сервера** (`SELECT VERSION(), @@sql_mode;` в phpMyAdmin): при нестрогом режиме важность валидации в API выше.
4. **Устраивают ли продуктово** выбранные границы: 255 для названий и контактов, 64 для единицы, 20 000 для заметок? Это решение владельца CRM, а не технический факт.
5. **Будет ли ручной ввод номера заказа** в будущем? Если да — нужна проверка уникальности и диапазона в форме, а не только в Zod.
