## 2. M3 — расположение document root и приватных каталогов

### Как код находит приватные файлы [лок]

1. `index.php` ищет каталог API (`apiRoot`) по двум кандидатам: `dirname(__DIR__)` (раскладка репозитория) и `dirname(__DIR__, 3) . '/devis-crm/api'`. Для `<home>/www/crm.devisd.online/api/index.php` второй кандидат — `<home>/devis-crm/api`.
2. Признак найденного каталога — наличие `src/bootstrap.php`. Если не найден — 503 `configuration_error` без `X-Request-Id`.
3. `DOCUMENT_ROOT` должен быть непустым и разрешаться через `realpath()`; `apiRoot` и `dirname(apiRoot)` тоже должны разрешаться и **оба** лежать вне document root (сравнение по границе каталога). Иначе — 503 `configuration_error`.
4. Конфиг: `dirname(apiRoot)/config/local.php` (`Application::create`), читается на первом обращении к БД.
5. Лог: `dirname(apiRoot)/logs/api.log` (`Logger::forPrivateRoot`), каталог создаётся с правами 0750; при неудаче запись уходит в `error_log()` PHP.

Все приватные пути выводятся из одного корня — если `apiRoot` найден верно, конфиг и логи согласованы автоматически.

## 3. M2 — статический аудит `.htaccess`

Текущий `api/public/.htaccess` (развёртывается в `<docroot>/api/`):

```apache
<IfModule mod_rewrite.c>
    RewriteEngine On
    RewriteBase /api/

    RewriteRule ^index\.php$ - [L]
    RewriteRule ^ index.php [L,QSA]
</IfModule>
```

### Ожидаемое поведение при работающем `mod_rewrite` и разрешённом `.htaccess` [предп]

| Запрос | Ожидание | Ответ API (подтверждено логикой и локально через router) |
|--------|----------|-----------------------------------------------------------|
| `/api/index.php` | первое правило — без rewrite, выполняется PHP | 404 JSON (путь `/` не маршрут) |
| `/api/health`, `/api/health/` | второе правило → `index.php`, `REQUEST_URI` сохраняется | 503 / 200 по конфигу |
| `/api/unknown`, несуществующие файлы и каталоги | → `index.php` | 404 JSON |
| `/api/index.php/health` | `^index\.php$` не совпадает → второе правило → `index.php` | как `/api/health` |
| **Существующие файлы внутри `/api/`**, кроме `index.php` | условия `-f`/`-d` нет → тоже переписываются на `index.php` | 404 JSON — файлы не отдаются |
| `/api/.htaccess` | обычно 403 от Apache до rewrite | HTML 403 или 404 JSON |
| `/api` без слэша | `mod_dir` может ответить 301 на `/api/` либо rewrite сработает сразу | 301 HTML или 404 JSON — оба приемлемы |
| Query string | `QSA` сохраняет; маршрутизация её игнорирует | без влияния |

### От чего зависят правила [ISP]/[разм]

- `mod_rewrite` загружен (иначе блок `IfModule` молча пропускается).
- `AllowOverride` разрешает `FileInfo` (иначе `.htaccess` игнорируется целиком или Apache отвечает 500 «not allowed here»).
- `Options FollowSymLinks` или `SymLinksIfOwnerMatch` (иначе rewrite в `.htaccess` даёт 403).
- Связка PHP: сообщено «PHP FastCGI (Apache)» **[польз]** — передача `REQUEST_URI` и `DOCUMENT_ROOT` в PHP.
- Наличие фронтенд-прокси (например, nginx) перед Apache — не известно. Если прокси отдаёт статические файлы сам по расширениям, он может обслуживать их **до** Apache и `.htaccess`.

### Риски, если `.htaccess` игнорируется или запрещён

| Ситуация | Последствие |
|----------|-------------|
| Нет `mod_rewrite` / `.htaccess` игнорируется | `/api/health` → HTML 404 Apache; любые файлы в `/api/`, кроме `index.php`, отдаются напрямую (`.php` — выполняются, остальное — как текст) |
| `RewriteEngine` запрещён `AllowOverride` | HTML 500 на все запросы к `/api/` (безопасно, но не JSON) |
| Нет `FollowSymLinks` | HTML 403 на все запросы к `/api/` |

### Может ли Apache ответить вместо JSON API

Да: 301 (`/api` без слэша, HTTP→HTTPS), 403 (`.htaccess`, симлинки), 404 (нет rewrite), 500 (запрещённая директива), 502/503/504 (FastCGI/прокси). Также при фатальной ошибке PHP до установки обработчиков (неподходящая версия PHP, запрещённый `ini_set`) — пустой или HTML-ответ. Это ограничение проверяется только на хостинге.

### Прямая выдача файлов из `/api/`

- По замыслу в `<docroot>/api/` лежат **только** `index.php` и `.htaccess`. `index.php` секретов не содержит. При таком составе прямая выдача безопасна даже без `mod_rewrite`.
- **Чувствительные файлы, которые нельзя размещать в document root:** `config/local.php` (реквизиты БД), `logs/api.log` (request id, коды ошибок, пути), `api/migrations/001_init.sql` (структура БД), `api/src/**` (исходники), `api/tests/**`. Если они окажутся в `/api/` и rewrite не работает (или их отдаёт фронтенд-прокси по расширению), они станут доступны. Поэтому до размещения нужно подтвердить работу rewrite и состав каталога.
- Код дополнительно отказывается работать, если приватный каталог лежит внутри document root (M1/M4), — но это не защищает файлы, случайно загруженные в `/api/` вручную.

### HTTP → HTTPS

Если на сайте включён принудительный редирект, запросы по `http://` получат 301 **до** PHP. Проверять API нужно сразу по `https://`. `curl -L` при 301 меняет `POST` на `GET` — проверка 405 через редирект даст ложный результат. Нужно отдельно проверить, что `Location` указывает на `https://crm.devisd.online` с тем же путём.

### Предлагаемые минимальные патчи (не применены, требуют согласования)

Вариант 1 — запрет всего в `/api/`, кроме `index.php`, независимо от `mod_rewrite` (Apache 2.4; требует, чтобы `AllowOverride` разрешал `AuthConfig`, иначе 500):

```apache
<FilesMatch "^(?!index\.php$).+">
    Require all denied
</FilesMatch>
```

Вариант 2 — убрать обёртку `<IfModule mod_rewrite.c>`, чтобы отсутствие `mod_rewrite` давало явную ошибку 500, а не молчаливую отдачу файлов. Минус: при отсутствии модуля всё `/api/` недоступно.

Решение — после того как в ISPmanager станет известно, что разрешено для `.htaccess`.

**Статус M2: открыт** — работа `.htaccess` подтверждается только на хостинге.

## 4. O1 — заголовок `X-Powered-By`

| Источник | Факт |
|----------|------|
| Код API | Заголовок **не добавляет**: в `api/` нет `X-Powered-By`, `header_remove`, `expose_php` **[лок]** |
| PHP | Добавляет при `expose_php = On`. Локально наблюдался `X-Powered-By: PHP/8.3.36`, т. к. локальный `php.ini` скопирован из `php.ini-development` (этап 3.5) **[лок]** |
| Веб-сервер / прокси | Может добавлять, удалять или оставлять заголовок — неизвестно **[разм]** |

`expose_php` — системная директива (уровень `php.ini`): её нельзя переключить через `ini_set()` во время выполнения.

### Варианты устранения (ничего не применялось)

1. **Основной:** выключить `expose_php` в настройках PHP сайта — **если такая настройка доступна** в ISPmanager на этом тарифе (не подтверждено).
2. **Запасной, отдельно согласовать:** удалять заголовок в коде (`header_remove('X-Powered-By')` в `JsonResponse::send()` и в отказах `index.php`) — работает независимо от `php.ini`.
3. Альтернатива на уровне веб-сервера: `Header unset X-Powered-By` в `.htaccess` (требует `mod_headers` и разрешения в `AllowOverride`) — тоже отдельное согласование.
4. После любого варианта — проверить итоговый HTTP-ответ (`curl -sI https://crm.devisd.online/api/health`).

**Статус O1: открыт** (низкий уровень, раскрытие версии PHP).

## 8. План будущей проверки (не выполнять без отдельного согласования)

Каждый этап — отдельное согласование. Этапы не объединяются.

### Этап I. Подготовка без размещения

*Уточнено на этапе 3.8.3:* до пунктов ниже — разовая диагностика окружения по `ONLINE_STAGE3_8_DIAGNOSTIC_SCRIPTS.md` (раздел 4, отдельное разрешение). Приватные каталоги, `local.php` и доступ к БД на сервере не создаются до анализа её результатов.

1. Получить ответы по чек-листу раздела 7.
2. По результатам: подтвердить или скорректировать раскладку (M3); выбрать вариант для `.htaccess` (M2) и для `X-Powered-By` (O1). Любая правка кода/`.htaccess` — отдельный согласованный этап с тестами.
3. Закоммитить текущие изменения (`index.php`, `run.php`, документы 3.4–3.6) — после согласования.

**Критерий перехода:** document root и `open_basedir` известны; решение по M2/O1 принято.

### Этап II. Первое размещение PHP API без конфигурации и без рабочих данных

1. Загрузить `api/src/` в `<home>/devis-crm/api/src/`; `api/public/index.php` и `.htaccess` — в `<docroot>/api/`. Ничего больше в document root. Способ передачи — подтверждённый до размещения, не обычный FTP (см. `ONLINE_STAGE3_4_DEPLOY_AUDIT.md`, п. 8.9).
2. **Не** загружать `local.php`, SQL, тесты, логи.
3. Проверить `https://crm.devisd.online/api/health`: ожидается **503 `configuration_error` с `X-Request-Id`**, запись в `<home>/devis-crm/logs/api.log`.

**Остановка и откат:** любой HTML-ответ вместо JSON, 503 без `X-Request-Id`, раскрытие путей/исходников, отдача файлов из `/api/` → удалить загруженные файлы `<docroot>/api/*` и `<home>/devis-crm/api/`, разобрать причину по журналу ошибок PHP.

### Этап III. Проверка HTTP/HTTPS и маршрутизации

1. `curl -i http://crm.devisd.online/api/health` — 301 на `https://` с тем же путём (если редирект включён).
2. По `https://`: `GET /api/health` (503), `GET /api/unknown` (404 JSON), `POST /api/health` (405 + `Allow`), `HEAD /api/health` (без тела), `GET /api` (301 или 404 JSON).
3. Заголовки: `Content-Type`, `Cache-Control: no-store`, `X-Content-Type-Options`, `X-Request-Id`, наличие `X-Powered-By` (O1).
4. Недоступность приватных путей: `/api/.htaccess`, `/devis-crm/...`, `/config/local.php`, `/api/src/...` → не отдают содержимое.
5. Ответы и `api.log` — без паролей, DSN, SQL, стеков; пути только в приватном логе.
