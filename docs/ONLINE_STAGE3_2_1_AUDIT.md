## 3. Найденные проблемы

### 3.1. Подтверждённые дефекты (исправлены)

| # | Критичность | Где | Суть |
|---|-------------|-----|------|
| D1 | Средняя | `Db.php` | `run()` превращает PHP warnings в `ErrorException`. mysqlnd при сбоях подключения или обрыве соединения выдаёт warning (например, `php_network_getaddresses…`, `MySQL server has gone away`) раньше `PDOException`. `catch (PDOException)` его не ловил, поэтому вместо **503 `db_unavailable`** был **500 `internal_error`**, а в лог попадал сырой текст warning'а с именем хоста. |
| D2 | Средняя | `Config::fromFile` | `is_file()` вне разрешённых путей `open_basedir` выдаёт warning → `ErrorException` → **500** вместо **503 `configuration_error`**. В лог при этом попадал текст warning'а. |
| D3 | Средняя (безопасность) | `index.php` | Если по ошибке выложить на сайт весь репозиторий или весь `api/`, первый кандидат пути `dirname(__DIR__)` молча срабатывал, и API «работал». При этом `config/local.php`, `logs/api.log`, `api/migrations/*.sql` и исходники `api/src` оказывались внутри document root. Логи и SQL отдаются как обычные файлы, а при отключённом PHP — и `local.php` с паролем. Ошибка размещения ничем не сигнализировалась. |
| D4 | Низкая | `Config.php` | `host` и `name` подставлялись в DSN через `sprintf` без проверки: значение с `;` добавляло произвольные опции DSN (например, `unix_socket`). Конфиг задаёт владелец, поэтому это скорее защита от опечаток, но проверка отсутствовала. |
| D5 | Низкая | `bootstrap.php` | Тело JSON кодировалось в `send()` вне `try`. Ошибка кодирования (невалидный UTF-8 в будущих данных) ушла бы в fatal-путь shutdown-обработчика. Сейчас это недостижимо (health отдаёт константы), но путь хрупкий. |
| D6 | Низкая (документация) | отчёт 3.2 | Шаг 8 ручного теста обещал 404 JSON для `/api/.htaccess`. На практике Apache обычно отвечает 403 ещё до rewrite. Описание 503 без `X-Request-Id` было неполным. Указано 17 тестов. |
| D7 | Тестируемость | `tests/run.php` | Не покрыты `index.php`, `run()` (буфер, `HEAD` без тела) и реальный путь PDO — критичные участки проверялись только через заглушки. |

### 3.3. Миграция `001_init.sql` — сверка с моделью CRM

Поля сверены один к одному с `clientSchema`, `orderSchema`, `orderItemSchema`, `paymentSchema` и Dexie `appMeta`.

| Таблица | Результат сверки |
|---------|------------------|
| `clients` | Все 14 полей есть. Обязательность совпадает: обязательны `name`, `isArchived` и метки времени, остальное nullable. `email` проверяется только в Zod — допустимо, проверка будет в API. |
| `orders` | Все 16 полей есть. ENUM статусов совпадает с `orderStatusSchema`. Деньги — `BIGINT ≥ 0`. `paid ≤ total` согласовано и с `assertPaidNotExceedsTotal`, и с валидацией бэкапа (`expectedPaid > expectedTotal` отклоняется), поэтому корректный бэкап не упрётся в CHECK. `number UNIQUE` совпадает с проверкой дублей в бэкапе. |
| `order_items` | Все 9 полей есть. `quantity > 0`, цены `≥ 0`. Отсутствие временных меток соответствует модели. |
| `payments` | Все 7 полей есть. `amount > 0` = `positiveMinorAmountSchema`. ENUM способов оплаты совпадает с `paymentMethodSchema`. |
| `app_meta` | key/value, JSON сохраняет тип значения. Без начальной строки, как в `allocateOrderNumber`. |
| Связи | `orders→clients RESTRICT` (клиента с заказами не удаляют), `order_items→orders CASCADE` (позиции переписываются с заказом), `payments→orders RESTRICT`. Колонки FK не участвуют в CHECK — ограничение MySQL 8 соблюдено. |
| MySQL 8 | Синтаксис совместим: JSON, `DATETIME(3)` с `CURRENT_TIMESTAMP(3)`, CHECK, ENUM, идентификаторы в обратных кавычках, ascii_bin для FK с обеих сторон. Длина индекса `name` (1020 байт) меньше лимита 3072. |

### 3.4. Разделение публичных и приватных файлов

| Ситуация | Что доступно по HTTP |
|----------|----------------------|
| Целевая раскладка (`api/public/*` в `<docroot>/api/`, остальное в `<home>/devis-crm/`) | Только `index.php` (исполняется). `local.php`, логи, SQL и `api/src` вне webroot — недоступны. |
| В `/api/` нет rewrite или игнорируется `.htaccess` | То же; `/api/health` — HTML 404, приватное не раскрывается. |
| PHP не исполняется в `/api/` | Исходник `index.php` без секретов (R3). |
| Весь репозиторий или `api/` целиком выложен в document root | **До аудита:** API работал, а логи, SQL и (без PHP) `local.php` были доступны. **После:** `index.php` отказывается работать (503 `configuration_error`, причина в журнале ошибок PHP). Сами файлы при этом лежат в webroot — их нужно убрать (защита D3 сигнализирует, но не прячет файлы). |
| `local.php` положен прямо в webroot | При работающем PHP файл исполнится и ничего не выведет; при отключённом PHP — утечка. API такой файл не прочитает (он ищет его рядом с приватным `api/`), поэтому ошибка проявится как 503 `configuration_error`. |

## 7. Рекомендации перед первым тестовым деплоем

1. **Прогнать PHP-тесты.** Нужен локальный PHP 8.3 с `pdo_mysql` (например, portable-архив с windows.php.net в отдельную папку). Установка — только с вашего согласия. Затем выполнить `php -l` для всех файлов и `php api/tests/run.php`.
2. **В phpMyAdmin до импорта:** `SELECT VERSION(), @@sql_mode;`. Ожидается MySQL ≥ 8.0.16 и `STRICT_TRANS_TABLES` в `sql_mode`. Если нет — сообщить до импорта.
3. **Решить S2** (лимиты строк): `.max()` в Zod или `TEXT` для контактов. Лучше до этапа CRUD, пока база пуста.
4. Подтвердить FTP-корень и возможность создать `/devis-crm/` рядом с `/www/`. Ограничения `open_basedir` посмотреть в настройках PHP сайта в ISPmanager, а не через публичный `phpinfo()`.
5. Выполнить ручной тест из раздела 12 отчёта 3.2. Ответ 503 без `X-Request-Id` теперь означает, что не найден приватный каталог или он оказался внутри document root; причину смотреть в журнале ошибок PHP.
6. Выкладывать на сайт **только** `api/public/index.php` и `api/public/.htaccess`; `api/src/` — только в `/devis-crm/api/src/`. `api/tests/`, `api/migrations/` и `config/local.php.example` на хостинг не нужны.
7. После проверки удалить `/www/crm.devisd.online/api-check/`.
8. Закоммитить этапы 3.2 и 3.2.1 отдельным коммитом после вашего подтверждения.
