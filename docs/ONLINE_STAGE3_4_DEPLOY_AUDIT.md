Это полезно: случайно загруженные в `/api/` файлы не отдадутся, а получат 404 JSON. Правила действуют только в `/api/`, фронтенд не затрагивают. Блок в `<IfModule mod_rewrite.c>`: без `mod_rewrite` правила молча не применяются (M2). |

### Что локально подтвердить нельзя

- Поведение Apache + FastCGI на REG.RU: обработка `.htaccess` (`AllowOverride`), наличие `mod_rewrite`, требование `Options FollowSymLinks`/`SymLinksIfOwnerMatch` для rewrite в `.htaccess`, значение `REQUEST_URI` после rewrite, наличие nginx-прокси перед Apache.
- Значения `DOCUMENT_ROOT`, `open_basedir`, `disable_functions`, расположение штатного `error_log` PHP. После этапа 3.4.1 это особенно важно: если `realpath()` не может разрешить document root или приватный каталог (например, из-за `open_basedir`), `index.php` откажет с 503.
- Реальная глубина document root относительно домашнего каталога и разрешение симлинков (`__DIR__` возвращает путь с раскрытыми симлинками).
- Возможность PHP читать `<home>/devis-crm/` и писать в `<home>/devis-crm/logs/`.
- Реальные HTTP-статусы и заголовки ответов (в CLI-тестах видно только тело).
- Подключение к MySQL REG.RU: хост (`localhost` через сокет или TCP), путь сокета по умолчанию для `pdo_mysql`.

## 4. Аудит SQL (`api/migrations/001_init.sql`)

| Аспект | Результат |
|--------|-----------|
| Синтаксис / MySQL 8 | Совместим с MySQL 8: InnoDB, `utf8mb4_unicode_ci`, `JSON`, `DATETIME(3)` + `CURRENT_TIMESTAMP(3)`, `ENUM`, CHECK, идентификаторы в обратных кавычках. **В реальной MySQL не выполнялся.** CHECK применяются только с MySQL 8.0.16 (MariaDB — с 10.2). |
| Типы и значения | UUID — `CHAR(36) ascii_bin`; деньги — `BIGINT` + CHECK ≥ 0, платёж > 0, `paid ≤ total`; статусы и способы оплаты — `ENUM`, совпадают с Zod; `quantity DOUBLE > 0`. |
| Ключи | PK у всех таблиц. FK: `orders→clients RESTRICT`, `order_items→orders CASCADE`, `payments→orders RESTRICT`; collation с обеих сторон FK — `ascii_bin`. Колонки FK не участвуют в CHECK (ограничение MySQL соблюдено). |
| Индексы | `uq_orders_number` (UNIQUE), индексы под реальные запросы: имя клиента, архив, дата/срок/статус заказа, `(client_id, order_date)`, `(order_id, sort_order)`, `(order_id, payment_date)`, `payment_date`. Длина индекса `name` (1020 байт) < 3072. |
| NULL / defaults / время | Обязательность совпадает с Zod. `DEFAULT 0` для денег и флагов, `status DEFAULT 'new'`. `created_at`/`updated_at` без DEFAULT — заполняет API (UTC). `schema_migrations.applied_at DEFAULT CURRENT_TIMESTAMP(3)` зависит от часового пояса сессии (L4). |
| Длины vs Zod | `VARCHAR(255)` ↔ `.max(255)`, `unit VARCHAR(64)` ↔ `.max(64)`: Zod 4 и MySQL оба считают кодовые точки. Шесть длинных полей — `MEDIUMTEXT` (≤ 16 МБ) при Zod `.max(20000)`: худший случай 80 000 байт помещается. |
| Целые | `orders.number`, `order_items.sort_order` — `INT UNSIGNED`, совпадает с Zod `.max(4 294 967 295)`. Деньги `BIGINT` шире JS-безопасного диапазона, Zod `.int()` ограничивает до 2⁵³−1. |
| Порядок создания | `schema_migrations` → `clients` → `orders` → `order_items` → `payments` → `app_meta` → `INSERT schema_migrations`. Зависимости соблюдены. |
| Повторный запуск | **Не идемпотентна по замыслу.** `schema_migrations` создаётся первой без `IF NOT EXISTS`: повторный импорт падает на первом же операторе, ничего не меняя. |
| Частичный импорт | DDL в MySQL фиксируется сразу. Если база **не пустая** (например, есть таблица `clients` от другого приложения), будет создана `schema_migrations`, затем ошибка — частичное состояние без строки `001_init`. Поэтому нужна **отдельная пустая база**. |
| Потеря данных | В файле нет `DROP`, `TRUNCATE`, `DELETE`, `UPDATE`, `ALTER` — существующие таблицы не изменяются и не удаляются. |

## 5. Рекомендуемая структура размещения

Плейсхолдеры: `<home>` — домашний каталог пользователя хостинга, `<docroot>` — document root сайта. Ожидается `<docroot>` = `<home>/www/crm.devisd.online` — **подтвердить**.

| Файл / каталог в репозитории | Где на хостинге | Доступ по HTTP | Примечание |
|------------------------------|-----------------|----------------|------------|
| `out/*` (сборка фронтенда) | `<docroot>/` | да | При синхронизации с удалением исключить `<docroot>/api/` |
| `api/public/index.php` | `<docroot>/api/index.php` | да (единственный PHP) | Секретов не содержит |
| `api/public/.htaccess` | `<docroot>/api/.htaccess` | нет | Требует `mod_rewrite` и обработки `.htaccess` |
| `api/src/**` | `<home>/devis-crm/api/src/` | нет | Вне document root |
| `config/local.php` (создаётся вручную из примера) | `<home>/devis-crm/config/local.php` | нет | Реквизиты БД; в Git не попадает |
| `logs/` | `<home>/devis-crm/logs/` | нет | Создаётся API автоматически, нужны права записи |
| `api/migrations/001_init.sql` | **не загружать** | — | Импортируется в phpMyAdmin с локального компьютера |
| `api/tests/`, `config/local.php.example`, `docs/`, `src/`, `node_modules/` | **не загружать** | — | |

### Совместимость с кодом

- Все приватные пути выводятся из одного корня `apiRoot`: конфиг = `dirname(apiRoot)/config/local.php`, логи = `dirname(apiRoot)/logs/api.log`. Если найден правильный `apiRoot`, остальное согласовано автоматически.
- `apiRoot` ищется в двух местах: `dirname(__DIR__)` (раскладка репозитория) и `dirname(__DIR__, 3) . '/devis-crm/api'`. Второй кандидат даёт `<home>/devis-crm/api` **только** при `__DIR__` = `<home>/www/crm.devisd.online/api`. Если document root глубже или в другом месте, либо путь идёт через симлинк, `index.php` ответит 503 `configuration_error` (безопасный отказ), а второй кандидат придётся поправить — это изменение кода, нужно согласование.
- Если FTP-пользователь ограничен каталогом сайта (chroot в `<docroot>`), создать `<home>/devis-crm/` через него не получится — понадобится основной пользователь ISPmanager или файловый менеджер панели.
- После этапа 3.4.1 `index.php` дополнительно требует, чтобы `DOCUMENT_ROOT`, `<home>/devis-crm/api` и `<home>/devis-crm` разрешались через `realpath()` и оба приватных пути были вне document root; иначе — 503 `configuration_error`.

## 8. План серверной проверки (выполнить позже, не на этом этапе)

Общее правило отчётов: **не публиковать** пароли FTP/MySQL, содержимое `local.php`, полный DSN, имена пользователей БД, полные абсолютные пути домашнего каталога (заменять на `<home>`), содержимое логов без вычитки, скриншоты панели с реквизитами.

Диагностические PHP-файлы (`phpinfo()` и т. п.) **не создаются**: роль диагностики выполняет сам `/api/health` (п. 8.8) — разные ответы однозначно указывают на причину. Тестовый каталог `/api-check/`, созданный ранее, удаляется в п. 8.11.

> **Пересмотрено на этапе 3.8** (отметка внесена на этапе 3.8.1). Решение выше было первоначальным. До размещения API предусмотрен отдельный одноразовый диагностический файл `tools/hosting-diagnostic.php`: он не использует `phpinfo()`, доступ к нему защищён одноразовым случайным ключом, выполняется ровно один HTTPS POST-запрос, после которого файл при любом исходе вручную удаляется через ISPmanager и проверяется его отсутствие. Запуск на сервере требует отдельного разрешения. На момент этой отметки запуск на хостинге **не выполнялся**; защита и удаление серверного файла в реальной среде не проверены. Процедура — `ONLINE_STAGE3_8_DIAGNOSTIC_SCRIPTS.md`.
>
> **Порядок (уточнено на этапе 3.8.3).** Сначала диагностика по `ONLINE_STAGE3_8_DIAGNOSTIC_SCRIPTS.md` (раздел 4, шаги 1–9) и анализ её результатов. Шаг 8.1 допускает только просмотр в ISPmanager.
