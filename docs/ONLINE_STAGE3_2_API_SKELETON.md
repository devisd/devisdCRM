## 3. Маршрутизация

**[реализовано]**

```text
HTTP  →  Apache (.htaccess в /api/)  →  api/public/index.php  →  bootstrap run()
      →  Request::fromServer()  →  Router::dispatch()  →  Controller  →  JsonResponse
```

- `.htaccess`: всё внутри `/api/` (кроме самого `index.php`) переписывается на `index.php` с сохранением query string. Правила лежат только в каталоге `/api/`, поэтому маршруты frontend (`/`, `/clients/…`, `/orders/…`) не затрагиваются; циклов нет (первое правило останавливает обработку для `index.php`).
- Блок обёрнут в `<IfModule mod_rewrite.c>`: без `mod_rewrite` сайт не падает с 500, но `/api/health` вернёт 404 от Apache. Резервный адрес без rewrite: `/api/index.php/health` — поддержан в `Request`.
- `RewriteBase /api/` и `Application::BASE_PATH = '/api'` — **API обязан находиться по URL `/api/`** в корне домена.
- Путь нормализуется: срезается `/api` (или `/api/index.php`), query string и завершающий `/`. `/api/health/` ≡ `/api/health`.
- Некорректный запрос → **400 `bad_request`**: метод не `[A-Z]{1,16}`, URI не начинается с `/` или начинается с `//`, длина > 2048, нулевой байт, невалидный UTF-8, отсутствует метод.
- Неизвестный путь → **404 `not_found`**. Известный путь с другим методом → **405 `method_not_allowed`** + заголовок `Allow`.
- `HEAD` обслуживается GET-обработчиком без тела ответа.
- Маршруты сейчас только точные, без параметров (`/clients/{id}` появятся на этапах CRUD).

Зарегистрирован один маршрут: `GET /api/health`. CRUD, импорт/экспорт, очистка БД, миграции через HTTP и выполнение SQL из запроса — **отсутствуют**.

## 4. Контракт JSON и healthcheck

### Конверт

```json
{ "ok": true, "data": { "status": "ok" } }
```

```json
{ "ok": false, "error": { "code": "not_found", "message": "Resource not found" } }
```

Заголовки ответов, сформированных приложением (`run()`, включая 500 при fatal error): `Content-Type: application/json; charset=utf-8`, `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`, `X-Request-Id: <16 hex>`. `Content-Type` нельзя переопределить.

Исключение — отказы самого `index.php` до запуска приложения (приватный код не найден или находится внутри document root): те же заголовки, но **без** `X-Request-Id`. Ответы, которые формирует не PHP (ошибки Apache, прокси, таймауты), этот контракт не покрывает.

### Коды ошибок, используемые сейчас

| HTTP | `code` | Когда |
|------|--------|-------|
| 400 | `bad_request` | Некорректный метод/URI |
| 404 | `not_found` | Неизвестный маршрут |
| 405 | `method_not_allowed` | Метод не поддерживается маршрутом |
| 500 | `internal_error` | Любое непредвиденное исключение или fatal error |
| 503 | `configuration_error` | Нет/неверный конфиг; приватный код API не найден; приватный каталог (с `config/` и `logs/`) находится внутри document root — проверка выполняется, только если `DOCUMENT_ROOT` задан и разрешается через `realpath`, иначе пропускается |
| 503 | `db_unavailable` | Нет драйвера `pdo_mysql`, ошибка подключения или `SELECT 1` |

Коды 201, 401, 403, 409, 422 поддерживаются `JsonResponse`, но появятся вместе с CRUD и авторизацией.

### `GET /api/health`

| Ситуация | Ответ |
|----------|-------|
| Конфиг есть, `SELECT 1` = 1 | **200** `{"ok":true,"data":{"status":"ok","db":true}}` |
| Конфига нет / плейсхолдеры / ошибка файла | **503** `configuration_error`, «Service is not configured» |
| БД недоступна | **503** `db_unavailable`, «Database is unavailable» |

Не раскрывает: версии PHP/MySQL, таблицы, пути, DSN, имя пользователя БД, текст исключений. Авторизация не требуется. Выполняется только `SELECT 1`; подключение открывается на каждый вызов health (нагрузка минимальная, но частый внешний мониторинг лучше не настраивать).

### Защита от утечек

- `display_errors=0`, warnings/notices превращаются в исключения, любой сторонний вывод отбрасывается буфером.
- Fatal error перехватывается shutdown-обработчиком → 500 JSON.
- `zend.exception_ignore_args=1`, stack traces не пишутся даже в лог.

## 5. Конфигурация и PDO

**[реализовано]**

- Конфиг — PHP-файл, возвращающий массив (`config/local.php.example`): `db.host`, `db.port` (по умолчанию 3306), `db.name`, `db.user`, `db.password`.
- Расположение: `<каталог над api/>/config/local.php`. В репозитории — `<repo>/config/local.php` (в `.gitignore`); на REG.RU — `<home>/devis-crm/config/local.php`, вне webroot (раздел 8).
- Значение `__CHANGE_ME__` из шаблона отвергается — неотредактированный пример не запустится.
- Ошибки конфигурации не содержат значений; синтаксическая ошибка в файле сообщает только тип ошибки (текст парсера мог бы процитировать пароль).
- Публичного fallback нет: без конфига API отвечает 503.

`Db`:

- Конфиг читается и соединение открывается **только** при первом `pdo()`/`ping()`; загрузка файлов и маршруты 404/405 БД не трогают.
- `ERRMODE_EXCEPTION`, `FETCH_ASSOC`, `EMULATE_PREPARES=false`, `ATTR_TIMEOUT=5`, DSN с `charset=utf8mb4`.
- Проверка наличия драйвера `pdo_mysql` → иначе 503 `db_unavailable`.
- Сообщение `PDOException` (может содержать имя пользователя БД) в лог не попадает — только SQLSTATE и код драйвера (например, 1045 — доступ запрещён, 2002 — нет соединения).

### Логирование

- Одна JSON-строка на ошибку: `time` (UTC), `level`, `request_id`, `code`, `message`, `exception`, `location`.
- Файл: `<каталог над api/>/logs/api.log` (на REG.RU — `<home>/devis-crm/logs/api.log`, создаётся автоматически с правами 0750).
- Если файл недоступен для записи — запись уходит в штатный `error_log()` PHP (журнал ошибок хостинга). **[проверить]** где ISPmanager хранит этот журнал.
- Маскирование `password=…`, `secret=…`, `token=…` и т. п.; ограничение длины сообщения 1000 байт.
- 4xx-ошибки не логируются (это поведение клиента, а не сбой).
- Ротации логов нет — следить за размером вручную.

## 6. Миграция `001_init.sql` и соответствие модели CRM

**[реализовано]** MySQL 8, InnoDB, `utf8mb4_unicode_ci`, внешние ключи, без данных и секретов. `utf8mb4_unicode_ci` выбрана вместо `utf8mb4_0900_ai_ci` для совместимости, если сервер окажется MariaDB.

| Таблица | Источник в коде | Ключевые решения |
|---------|-----------------|------------------|
| `schema_migrations` | новая, учёт миграций | создаётся первой **без** `IF NOT EXISTS`: повторный импорт падает сразу, ничего не меняя; в конце файла вставляется `001_init` |
| `clients` | `clientSchema` | все поля модели; `tags` → `JSON NULL`; индексы `(name)` и `(is_archived, name)` под `listClients` |
| `orders` | `orderSchema` | `number` `UNIQUE`; `status` ENUM из `orderStatusSchema`; деньги `BIGINT`; `CHECK (paid_minor <= total_minor)` = `assertPaidNotExceedsTotal`; FK на клиента `RESTRICT` (клиентов с заказами архивируют, не удаляют); индексы `(client_id, order_date)`, `order_date`, `due_date`, `status`, `is_archived` — как в Dexie |
| `order_items` | `orderItemSchema` | `quantity DOUBLE` + `CHECK > 0`; цены/суммы `BIGINT`; FK `ON DELETE CASCADE` (позиции переписываются вместе с заказом); индекс `(order_id, sort_order)` |
| `payments` | `paymentSchema` | `amount_minor BIGINT` + `CHECK > 0`; `method` ENUM из `paymentMethodSchema`; FK `RESTRICT` (история оплат не удаляется неявно); индексы `(order_id, payment_date)`, `payment_date` (выручка за период) |
| `app_meta` | Dexie `appMeta` | `meta_value JSON` (в Dexie значение string/number/boolean); без начальной строки: отсутствие `nextOrderNumber` = 1, как в `allocateOrderNumber` |

Сознательные решения, требующие внимания на следующих этапах:

1. **Даты.** Все даты в CRM — ISO-строки UTC (`toISOString`; даты из форм — локальный полдень в UTC). В БД — `DATETIME(3)` в UTC. Преобразование ISO ↔ DATETIME будет в PHP; `isoDateTimeSchema` в бэкапе проверяет только непустую строку, поэтому импорт должен отклонять нераспознаваемые даты (422).
2. **Количество.** В CRM — произвольное дробное число без ограничения точности (`^\d+(\.\d+)?$`). `DOUBLE` хранит то же IEEE-754 значение, что и JS, поэтому `round(qty × price)` совпадёт. `DECIMAL` ввёл бы новое правило округления, которого в CRM нет. Целочисленность для «шт.» проверяется в форме — на сервере её надо будет повторить в API.
3. **Длина строк.** *На момент этапа 3.2:* `VARCHAR(255)` для имён, названий и контактов, `VARCHAR(64)` для единицы, `TEXT` для описаний и заметок; в Zod лимитов не было. *Актуально:* лимиты 255 / 64 / 20 000 заданы в Zod и формах (этап 3.2.4); `other_contact` и пять полей описаний, заметок и комментария — `MEDIUMTEXT` (этап 3.2.5). Zod 4 считает длину в кодовых точках Unicode, как MySQL для `VARCHAR`. В PHP API при CRUD нужна та же проверка через `mb_strlen()` (422).
4. **Правила денег, не выразимые в SQL** (итог = сумма позиций − скидка, скидка ≤ сумма позиций, платёж ≤ остаток) — обязанность API в транзакциях, как в `recalculateOrderMoney`.
5. **Пользователи и сессии не созданы.** Схема авторизации ещё не выбрана (см. 3.1, риск 7) — таблицы появятся отдельной миграцией `002` на этапе авторизации. Учётных записей и паролей в миграции нет.

## 7. Импорт SQL через phpMyAdmin

1. В ISPmanager создать базу MySQL и пользователя с доступом только к ней (если ещё нет). Пароли мне присылать не нужно.
2. Открыть phpMyAdmin, **выбрать именно эту базу** (она должна быть пустой).
3. Импорт → выбрать файл `api/migrations/001_init.sql` → кодировка `utf-8` → выполнить.
4. Проверить: есть таблицы `schema_migrations`, `clients`, `orders`, `order_items`, `payments`, `app_meta`; запрос `SELECT * FROM schema_migrations;` возвращает строку `001_init`.
5. Повторный импорт завершится ошибкой на первой же таблице — это ожидаемая защита.
6. Если импорт оборвался на середине (DDL в MySQL не откатывается): база пустая по данным, поэтому удалить созданные таблицы в phpMyAdmin и импортировать файл заново.

Миграция не применяется автоматически ни при запросах API, ни при сборке frontend.

## 12. Ручное тестирование на хостинге (пошагово)

Выполнять только после отдельного решения о тестовом деплое.

1. **Миграция:** импорт `001_init.sql` в пустую базу через phpMyAdmin (раздел 7).
2. **Приватный код:** создать `/devis-crm/api/` рядом с `/www/` и загрузить туда `api/src/`.
3. **Публичная часть:** загрузить `api/public/index.php` и `api/public/.htaccess` в `/www/crm.devisd.online/api/`.
4. **Без конфига** открыть `https://crm.devisd.online/api/health`:
   - ожидается **503 JSON `configuration_error` с заголовком `X-Request-Id`** → приватный код найден, конфига пока нет;
   - 503 JSON **без** `X-Request-Id` → `index.php` не нашёл `/devis-crm/api` (путь или `open_basedir`) либо отказался работать, потому что приватный каталог оказался внутри document root (причина — в журнале ошибок PHP хостинга);
   - HTML 404 от Apache → не работает rewrite; проверить `https://crm.devisd.online/api/index.php/health`;
   - HTML 500 → директива в `.htaccess` запрещена настройками сервера.
   - Проверить, что появился `/devis-crm/logs/api.log` со строкой `configuration_error` (если нет — запись ушла в журнал ошибок хостинга).
5. **Конфиг:** локально скопировать `config/local.php.example` → заполнить реальными данными → загрузить как `/devis-crm/config/local.php`. В Git не добавлять. Права — минимально необходимые.
6. Повторить `/api/health` → **200** `{"ok":true,"data":{"status":"ok","db":true}}`. При **503 `db_unavailable`** смотреть код драйвера в `api.log`.
7. `https://crm.devisd.online/api/unknown` → 404 JSON; `POST /api/health` → 405 + `Allow: GET, HEAD`.
8. `https://crm.devisd.online/api/.htaccess` → 403 от Apache или 404 JSON — главное, что содержимое файла не отдаётся.
9. `https://crm.devisd.online/` и страницы frontend открываются как раньше.
10. После проверки удалить тестовый каталог `/www/crm.devisd.online/api-check/`.
