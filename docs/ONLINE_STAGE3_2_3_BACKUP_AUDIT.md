## 4. Замечание о Unicode

Предлагаемые проверки Zod `.max()` считают длину по `string.length` (UTF-16-единицы); MySQL `VARCHAR(n)` — в символах (кодовых точках). Для символов вне BMP (эмодзи и т. п.) JS даёт длину 2, MySQL — 1. Поэтому проверка по `string.length` **строже** MySQL: значение, прошедшее Zod, всегда поместится в столбец. Обратное неверно: строка длиной 256 по JS может уложиться в `VARCHAR(255)` MySQL. При реальной проверке это стоит учитывать как возможные «ложные» превышения около границы.

Безопасность ограничений можно считать подтверждённой при одном из условий:

1. Владелец CRM подтверждает, что реальных данных и бэкапов нет (так указано в плане миграции: «реальных данных для переноса нет»).
2. Если копии есть — их нужно проверить тем же способом: локально, только чтение, вывод только длин и счётчиков. Для этого нужно либо указать путь к файлу, либо положить копию в проект во временный неотслеживаемый каталог (например, `local-backups/`, предварительно добавив его в `.gitignore`).
3. Данные, которые остались только в IndexedDB браузера, сначала экспортировать через «Настройки → Экспорт JSON» и проверить файл.
