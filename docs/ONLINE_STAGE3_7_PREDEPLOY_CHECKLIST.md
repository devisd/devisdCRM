## 3. Ранние отказы API

### Как устроены ответы (по коду)

- `index.php` до подключения приложения проверяет раскладку. При отказе вызывается `$refuse()`: `error_log('devis-crm-api: <причина>')`, статус 503, заголовки `Content-Type: application/json; charset=utf-8`, `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`, тело `configuration_error`, `exit`. **`X-Request-Id` не создаётся** — он генерируется только в `run()` (`bootstrap.php`), которая ещё не вызвана.
- Если раскладка в порядке, ответы формирует приложение (`Application::handle`): у всех есть `X-Request-Id`; ошибки конфигурации и БД пишутся в приватный `api.log` с тем же request id (при недоступности каталога логов — в журнал ошибок PHP).
- Тело ответа для клиента **одинаковое** у раннего отказа и у ошибки конфигурации приложения. Различаются только наличие `X-Request-Id` и место, где записана причина. Это сделано намеренно: клиент не получает сведений о путях.

### Таблица

| Сценарий | HTTP | Тело | `X-Request-Id` | Причина записывается | Чем проверено |
|----------|------|------|----------------|----------------------|---------------|
| Приватный каталог API не найден | 503 | JSON `configuration_error` | нет | журнал ошибок PHP: `private API directory not found` | только по коду; тестом и HTTP **не проверялось** |
| `DOCUMENT_ROOT` пустой или не разрешается | 503 | JSON `configuration_error` | нет | журнал ошибок PHP: `document root is unknown or cannot be resolved` | CLI-тест (3.4.1), HTTP M4a/M4b через обёртку (3.5) |
| Приватный путь не разрешается через `realpath()` | 503 | JSON `configuration_error` | нет | журнал ошибок PHP: `private API directory cannot be resolved` | только по коду; **не проверялось** |
| Приватный каталог (или его родитель) внутри document root | 503 | JSON `configuration_error` | нет | журнал ошибок PHP: `private API directory is inside the document root` | CLI-тесты, HTTP M1/P1 (3.5) |
| Конфигурация отсутствует | 503 | JSON `configuration_error` | **есть** | `<home>/devis-crm/logs/api.log`: `"code":"configuration_error"` и request id | CLI-тест, HTTP A1–A3 (3.5) |

| База недоступна | 503 | JSON `db_unavailable` | **есть** | `api.log`: `"code":"db_unavailable"`, SQLSTATE и код драйвера | CLI-тест (реальный PDO на закрытый порт), HTTP A13 (3.5) |

### Корректировка критерия первого размещения (без `local.php`)

| Ответ `GET https://crm.devisd.online/api/health` | Значение | Действие |
|---------------------------------------------------|----------|----------|
| 503, JSON `configuration_error`, **есть** `X-Request-Id`, в `api.log` запись с тем же request id | **Ожидаемый результат**: код найден, раскладка прошла проверки, конфига ещё нет | Переход к проверкам HTTP/Apache |
| 503, JSON `configuration_error`, **есть** `X-Request-Id`, записи в `api.log` нет | Раскладка в порядке, но PHP не может писать в `<home>/devis-crm/logs/` | Остановиться; найти запись по request id в журнале ошибок PHP; уточнить права |
| 503, JSON `configuration_error`, **нет** `X-Request-Id` | **Ранний отказ** `index.php` — не дефект кода, а сигнал о раскладке/окружении | Остановиться; причину смотреть в журнале ошибок PHP (одна из четырёх строк таблицы выше) |
| HTML-ответ, пустой ответ или иной JSON | Ответ веб-сервера или ошибка до API | Остановиться; см. раздел 6 |

Пункт 3 «Этап II» в `ONLINE_STAGE3_6_HOSTING_READINESS.md` («ожидается 503 `configuration_error` с `X-Request-Id`») верен; этот раздел дополняет его разбором ответов без `X-Request-Id` и без записи в `api.log`.

### Этап 2. HTTP/HTTPS и Apache (после отдельного разрешения)

- Все проверки API — по `https://`.

- Маршрутизация: `GET /api/health` (503), `GET /api/unknown` (404 JSON), `POST /api/health` (405 + `Allow: GET, HEAD`), `HEAD /api/health` (без тела), `GET /api` (301 или 404 JSON).
- Заголовки: `Content-Type`, `Cache-Control: no-store`, `X-Content-Type-Options`, `X-Request-Id`, наличие `X-Powered-By`.
- Отличать ответ API (JSON с полем `ok`, наши заголовки) от ответа веб-сервера (HTML, без `X-Request-Id`).
- Недоступность приватных файлов (раздел 6).

**Остановка:** отдача содержимого файлов, путей, исходников; маршрутизация не работает.

### Откат — без автоматического удаления

## 6. Защита публичного каталога `/api/`

### Разрешено в `<docroot>/api/`

- `index.php` — единственный PHP-файл, секретов не содержит;
- `.htaccess`.

Ничего больше.

### Должно оставаться вне document root

`<home>/devis-crm/api/src/` (исходники), `<home>/devis-crm/config/local.php` (реквизиты БД), `<home>/devis-crm/logs/` (логи). Не загружаются на хостинг вообще: `api/migrations/001_init.sql` (импортируется отдельно через phpMyAdmin), `api/tests/`, `config/local.php.example`, `docs/`, исходники фронтенда.

### Если `.htaccess` игнорируется или нет `mod_rewrite`

- Текущий `.htaccess` защищает файлы **только через rewrite** внутри `<IfModule mod_rewrite.c>`. Без `mod_rewrite` или при игнорировании `.htaccess` блок молча не применяется — **защиты нет**.
- Тогда `/api/health` даст HTML 404, а любые файлы в `/api/`, кроме `index.php`, будут отданы напрямую (`.php` — выполнены, остальное — как текст).
- При разрешённом составе каталога (только `index.php` и `.htaccess`) отдавать нечего — поэтому состав каталога и есть основная защита до подтверждения M2.
- Если перед Apache стоит прокси, отдающий статику сам, он может отдавать файлы по расширению независимо от `.htaccess`.

### Проверки

| Когда | Проверка |
|-------|----------|
| До размещения | Список файлов для `<docroot>/api/` = `index.php` + `.htaccess`; в загружаемом наборе нет `local.php`, SQL, логов, тестов; ответы по пунктам 10–11 чек-листа |
| После размещения (этап 1–2) | Файловым менеджером: в `<docroot>/api/` только два файла. По HTTPS: `/api/.htaccess` не отдаёт содержимое; запросы к `/config/local.php`, `/devis-crm/…`, `/api/src/…`, `/api/migrations/…` не отдают содержимое (404/403) |

Ранее предложенные патчи `.htaccess` (`FilesMatch` с `Require all denied`; отказ от `IfModule`) — **не применены**, остаются предложением для согласования после ответов по пункту 10 чек-листа.
